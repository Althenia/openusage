Investigation was offline: no login, credential reads from the YCoding database, or requests to Meta were performed. The inspected native artifact is `/Users/viadz/.local/bin/muse-bin-1.4.7-R6101.1`, Mach-O arm64, SHA-256 `87ff5a31b63e30b6ac04d3e8298285517e753c126fb6f3aee80accf28c4562f1`. `muse schema generate-json-schema --out <temporary-directory>` succeeded offline. ## 1. Credentials and storage

### Muse CLI and launcher

- **Launcher file path:** `MUSE_AUTH_PATH` overrides the path; otherwise it reads `$XDG_CONFIG_HOME/muse/auth.json`, or `$HOME/.config/muse/auth.json` when `XDG_CONFIG_HOME` is unset (`/Users/viadz/.local/bin/muse`, lines 19–25).
- **Fields actually read by the launcher:** root `providers` object → `meta` object → `mechanism: "oauth"` → nonempty string `access_token`; optional `expires_at` is accepted only as a nonnegative-digit JSON number (`muse`, lines 472–493). The launcher does not interpret or compare that expiry value (lines 503–513). Its unit and whether it is wall-clock absolute time are **unknown** from the launcher.
- **Other fields/credential sources:** the launcher does not read `refresh_token`, account ID, user ID, or a keychain; it reads no `MUSE_*_TOKEN` variable. Its credential-related environment variables are `MUSE_AUTH_PATH` and `MUSE_LOGIN` (the latter controls optional re-login; lines 649–656). This is the launcher's behavior, not a complete inventory of the binary's credential backend.
- **Native binary credential schema:** embedded strings at file offset `0x1193320d` include `OAuthTokens`, `access_token`, `refresh_token`, `expires_at`, `obtained_via`, `api_key`, `api_base_url`, `user_full_name`, `user_email`, `user_avatar_url`, and `subs_active`; the nearby type string says `struct OAuthTokens with 10 elements` at `0x11939511`. The binary also contains `ProviderCredential` and `secret_schema_version` at `0x119332b8`. This identifies embedded serialized field names, but not the full on-disk JSON envelope, which values are required, or an account/user-ID field. It does not establish that all fields are populated.
- **Keychain:** the binary links Security.framework and references `kSecAttrAccount`, `kSecAttrService`, `SecItemCopyMatching`, `SecItemUpdate`, and `SecItemAdd` (file offsets `0x1515db4b`–`0x15167a94`). Embedded error text explicitly refers to Meta credentials in macOS Keychain (for example `0x119531a5`). Exact Keychain service/account values were not recovered. A local inventory showed only `~/.config/muse/.auth.json.lock`, not an `auth.json`; it establishes no logged-in CLI file credential.

### OpenUsage/YCoding caller credential (additional verified caller context)

- Installed YCoding 0.10.5's supplied credential row is SQLite `credential`, `integration_id='meta'`, with JSON value shape `{"type":"key","key":"<redacted>"}`. The secret was not opened, printed, or sent. This is an API key, not the Muse CLI's OAuth `providers.meta` file format.
- The inspected YCoding source may be newer than installed 0.10.5: it uses `integrationID = "muse"` (line 15), while the supplied installed credential row has `integration_id='meta'`. It registers `META_API_KEY` as its environment credential (lines 307–311); `keyFor` uses a stored key as-is, otherwise requires an OAuth credential (lines 225–232). The Muse CLI likewise says `META_API_KEY` takes precedence over its account login (`muse login --help`) and `muse auth set` reads a key from stdin, defaulting to provider `meta` (`muse auth set --help`). These help commands were offline.
- **YCoding API-key request form:** base URL is `https://api.meta.ai/v1` (source line 19). The API key is sent as `Authorization: Bearer <key>` with `x-client-id: tbh:exec`; source lines 355–368 set these headers and route model calls to `/responses`. It also sets session headers `x-tbh-session-id` and `x-meta-ai-gateway-session-id` (lines 359–362). No key value is included here.

## 2. Device authorization, refresh, and API-key minting

- **Launcher device authorization:** `POST https://auth.meta.com/oidc/device/authorization/`, form field `client_id=1031625952748946` (`muse`, lines 7–12, 416–437, 539–540). It requests JSON, sends `User-Agent: muse-code/launcher-3` and `Accept: application/json`, and follows no redirects (lines 14–16, 425–436).
- **Launcher device token grant:** `POST https://auth.meta.com/oidc/device/token/`, form fields `grant_type=urn:ietf:params:oauth:grant-type:device_code`, `device_code`, and the same `client_id` (lines 610–613). Success requires response `access_token` (lines 496–500, 614–621); device polling recognizes `authorization_pending`, `slow_down`, `access_denied`, and `expired_token` (lines 628–644). No refresh grant/request is implemented by the launcher.
- **Native/YCoding login contract:** current YCoding source corroborates those device endpoints and fields (`muse.ts`, lines 66–129); its decoder recognizes response `access_token`, `refresh_token`, and `expires_in` (lines 32–36) and computes expiry in milliseconds (lines 106–114). It stores the OAuth refresh value if present, but the inspected key-mint path checks access-token expiry and asks the user to log in again rather than refreshing it (`muse.ts`, lines 133–145, 225–232). Thus no refresh endpoint/grant/form is evidenced for this current caller.
- **OAuth-to-Muse-key mint (YCoding OAuth path):** `POST https://api.meta.ai/muse-code/key` with `Authorization: Bearer <OAuth access token>`, `x-api-version: 1.0.0`, JSON body `{"onboard":false}` (`muse.ts`, lines 133–145). It accepts optional response fields `api_key`, `base_url`, `require_payment`, `action_url`, `is_subs_active`, and `subs_tier_name` (lines 38–45). It requires the first two and rejects `require_payment: true` or `is_subs_active: false` (lines 146–155). This API-key mint is separate from the normal API-key login path.
- **Expiry/401 handling in YCoding:** OAuth access-token expiry is an absolute millisecond timestamp; expired tokens require reconnect (`muse.ts`, lines 22, 133–135, 230). A 401/403 from key mint produces the same reconnect error (lines 143–145). For a 401 on a model request using OAuth, YCoding discards the cached minted key, mints again, and retries once; a second 401 becomes reconnect-required (lines 369–380). The shown code has no refresh-token grant.
- The native binary contains strings for device token fields and errors such as `token response carried an empty access token` (offsets `0x10ff3698`, `0x10ff4b77`) and the device-token endpoint/grant (`0x10ff4d8e`), but strings alone do not establish a different native refresh flow.

## 3. Subscription usage/quota request and display

### Upstream API request

- **No dedicated subscription usage/quota endpoint was established.** Offline binary searches found no literal `/muse-code/usage`, `/muse-code/quota`, `/muse-code/subscription`, GraphQL document ID, or `x-ratelimit-*` header string. Search covered printable strings and byte occurrences for these names, related usage/quota/subscription terms, and Meta hosts; it is not a full disassembly proof that such a request does not exist.
- The provider source currently requests `/muse-code/key`, `/muse-code/models`, and `/responses` for its identified flows (`muse.ts`, lines 133–168, 363–368). It contains no subscription usage call or usage response decoder. `/muse-code/models` uses the minted/API key as `Bearer` plus `x-client-id: tbh:exec` (lines 162–170); the `/responses` route uses the same key/header wrapper for direct-key or minted-key flows (lines 225–243, 355–368). This does **not** prove that a separate upstream quota endpoint accepts either credential type.
- The binary's embedded Model API stream decoder includes `SubscriptionUsageEvent` and related snapshot types: `SubscriptionUsageSnapshot`, `SubscriptionWindowSnapshot`, and `SubscriptionWeeklySnapshot` (strings around offsets `0x111809e8`, `0x11182107`, `0x11184038`, `0x11184202`). Field names include `window`, `weekly`, `tier`, `used_percent`, `resets_at`, and `window_duration_mins` (offsets `0x11182107`, `0x11184038`, `0x11160ada`). The decoder labels stream events including `subscription` at `0x111809e8`; this is evidence of a stream payload path, not of a dedicated quota URL or actual response instance.
- The native binary refers to `tbh_model::subscription_usage::SubscriptionUsageSource::latest_stream_usage` at offset `0x152e582e`, and TUI `tbh_tui::subscription_usage` / `session_status` code at offsets `0x111b079d`, `0x111cab50`. These are compiler-embedded names, not a function decompilation; REA's native string/function provider was unavailable. Exact request method, URL, headers, body, and whether subscription stream data is received only during `/responses` are **unknown**.
- **YCoding API key vs OAuth acceptance:** the sources prove OAuth is used for `/muse-code/key`, while the resulting key or direct `META_API_KEY` is used for `/muse-code/models` and `/responses`. No source or binary evidence establishes the credential accepted by a distinct subscription endpoint because that endpoint was not found.

### Available usage shape and UI labels

- The binary's own offline MSP schema export defines local `usage/read` as a host read of last-observed subscription usage (schema description at `msp.schema.json` `$defs/UsageReadResult` and method `usage/read`; generated only under `/tmp` and removed afterward). It is not an upstream Meta route. The schema's `SubscriptionUsage` fields are `window`, `weekly`, `tier`, and `observedAtMs`; window fields are `usedPercent`, `windowDurationMins`, and `resetsAtMs`; weekly fields are `usedPercent` and `resetsAtMs` (schema `$defs/SubscriptionUsage`, `SubscriptionUsageWindow`, `SubscriptionUsageWeekly`). Descriptions say percentages are provider values, integers ≥0 including >100, and reset stamps are epoch milliseconds. This is a local protocol representation, not proof of raw Meta JSON names or encoding.
- **Native stream snapshot names/semantics:** the binary's stream structs use snake_case fields `used_percent`, `resets_at`, and `window_duration_mins`, with `window` and `weekly` blocks. The binary schema maps them into the local camelCase `usage/read` shape above; whether its source normalization exactly reflects Meta's raw JSON is unverified without decompilation or a real response.
- **No used/limit/count values:** observed stream/schema fields contain percentages and resets, not numeric used and limit quantities. A tier field exists, but the actual tier labels and actual values are unknown. No spend/credits fields are part of this subscription shape.
- **TUI text:** the binary includes a status-bar item `Quota` and description `Subscription usage: current window and week` at file offset `0x111d1bf8`. Help/command text at `0x111abb21` and `0x112a9842` advertises `/usage` as showing session usage/cost/context and `/status` as current session status/usage. The `/subscription` command appears as retired (`0x114433f5`). These strings establish labels and command descriptions, not a live output sample or exact formatting of quota values.

## 4. Errors and no-subscription behavior

- **Device authorization:** launcher distinguishes redirect (never follows it), unavailable 404, other non-2xx start failures, denied consent, expired device code, pending, and slow-down (`muse`, lines 541–555, 623–644). These are device-login outcomes, not errors from an upstream usage call.
- **YCoding subscription/payment gate:** if key mint returns `require_payment: true` or `is_subs_active: false`, it fails with `Muse subscription/payment setup is required` and includes the optional `action_url` (`muse.ts`, lines 149–152). The real response values were not fetched.
- **Expired/rejected account token:** YCoding's key-mint 401/403 is reported as “Muse account token expired or was rejected; log in again”; expired local access tokens produce the same reconnect guidance (`muse.ts`, lines 22, 133–145). A model-call 401 is retried once with a new minted API key, then reconnect is required (`muse.ts`, lines 369–380). No error body shape for Meta was obtained.
- **Binary error strings:** the embedded stream/parser vocabulary includes `auth_error`, `rate_limited`, `account_restricted`, `invalid_request`, and `model_not_found`, and generic `retry_after`/`request_id` strings (offsets `0x111809e8`, `0x1117389d`). This does not tie any one error to a usage endpoint or prove its HTTP status/body shape.
- **Unknown:** exact HTTP 401/expired-token and no-subscription error response JSON from Meta; any usage-specific 401/403 behavior; whether API-key or OAuth-only auth is required for subscription data; native CLI output for a live `/usage` call.

## Confirmed vs. unknown

**Confirmed:** launcher auth-file path and consumed fields; device-code request endpoints/forms/client ID; CLI key input and `META_API_KEY` priority; YCoding key-vs-OAuth paths, key-mint fields, and request headers; binary subscription-stream/local schema fields; quota TUI label and `/usage`/`/status` help text; no dedicated usage endpoint string found in the bounded static search.

**Unknown:** complete native `auth.json`/Keychain schema and exact Keychain labels; launcher expiry units and any CLI refresh request; a subscription usage HTTP endpoint/method/headers/body or credential requirements; raw Meta usage JSON and real values; numeric used/limit or spend/credits; live output/error bodies and exact 401/no-subscription semantics.

## Live verification

The owner verified Muse CLI login storage and one real streaming request. `auth.json` has `schema_version: 2` and `providers.meta` fields `mechanism: "oauth"`, `storage: "keychain"`, `obtained_via: "device_code"`, `api_base_url`, `subs_active`, and account display metadata; it contains no tokens. The API key and access token are in the Keychain generic password item at service `ai.meta.dev.credentials`, account `meta`; no refresh token or expiry is stored. No key or account-identifying value is recorded here.

Usage comes from one streamed `POST https://api.meta.ai/v1/responses` request with `Authorization: Bearer <api_key>`, `x-client-id: tbh:exec`, JSON content type, and body `{"model":"muse-spark-1.2","input":"hi","max_output_tokens":16,"stream":true,"store":false,"reasoning":{"effort":"minimal"}}`. Consume the complete SSE body; the final `response.subscription_usage` event contains `subscription.tier`, `weekly.{resets_at,used_percent}`, and `window.{resets_at,used_percent,window_duration_mins}`. `resets_at` is epoch seconds, percentages are integer values (may exceed 100), the window is 300 minutes, and weekly is 10080 minutes (Monday 00:00 UTC reset). Tier is an opaque numeric ID. Non-streaming replies have no usage event; the plain YCoding `LLM_…` API-key path does not produce subscription usage. The refresh call consumes a small model request; there is no separate quota endpoint.
